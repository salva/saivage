# Runtime-Owned Tool Fields Remediation Plan

> **Adversarial review applied 2026-06-07.** All schema claims, code references,
> and flow descriptions have been verified against source. Corrections and missing
> concerns are marked with **[REVIEW]** inlines and a dedicated section below.

## Problem

Several Saivage v2 tool contracts expose persisted artifact shapes directly to
agents. This makes agents provide metadata that the runtime already knows or
should own, such as timestamps, durations, generated IDs, and command-log file
names.

This creates avoidable failures:

- Agents fabricate timestamps to satisfy schemas.
- Agents omit required runtime metadata and receive validation errors after
  doing useful work.
- Agents infer they should choose internal paths such as shell stdout/stderr
  logs.
- Persisted schemas become coupled to LLM-facing tool input schemas.

The desired rule is:

> Agents provide semantic intent and evidence. The runtime provides operational
> metadata, generated IDs, timing, canonical paths, and persistence envelopes.

## Scope

In scope:

- In-process MCP tool schemas exposed to agents.
- Plan/stage artifact writer tools.
- Worker and manager prompts that describe required tool payloads.
- Runtime enrichment before writing canonical artifacts.
- Tests for strict persisted artifacts and permissive agent-facing input.

Out of scope:

- Rewriting the agent hierarchy.
- Relaxing persisted artifact schemas as the source of truth.
- Removing role write-territory enforcement.
- Changing provider routing or model behavior.

## Design Principles

1. **Persisted artifacts remain strict.**
   `TaskList`, `TaskReport`, `StageSummary`, and plan/history files should
   continue to have complete canonical metadata on disk.

2. **Agent-facing inputs should be minimal.**
   Tool schemas should require only fields that express the agent's intent or
   findings.

3. **Runtime-owned values are never requested from agents.**
   This includes timestamps, durations, generated IDs, runtime output paths,
   and author/agent identity when available from context.

4. **Explicit agent-selected paths remain guarded.**
   Some tools legitimately need caller-selected paths, such as
   `write_file.path` and `download_file.path`. These continue through
   role/path authorization.

5. **Runtime-generated paths are not agent input.**
   If a path is internal runtime I/O, such as shell command logs, it should be
   generated by the runtime and returned in the result.

6. **Existing on-disk state remains readable.**
   Any change should preserve compatibility with current
  `.saivage/stages/**` artifacts.

7. **[REVIEW: new principle] Three validation gates must all be updated.**
   There are three separate gates that enforce what agents must provide:
   (a) Zod schema validation via `Schema.parse()`, (b) JSON Schema in tool
   `inputSchema` shown to LLMs, and (c) prompt text that instructs agents what
   to include. Changing only one or two of these leaves agents still trying to
   fabricate the old fields or receiving confusing instructions. All three
   must be updated in lockstep.

## Current Contract Issues

### Task Lists

**Current exposed tool** (`src/mcp/plan-registry.ts:154-168`):

```ts
stage_write_tasks({ task_list })
```

Tool description explicitly says: *"TaskList object with stage_id, created_at,
updated_at, and tasks."*

**Current persisted schema** (`src/types.ts:140-145`, `TaskListSchema`) requires:

| Field | Type | Required | Default |
|---|---|---|---|
| `stage_id` | `z.string()` | yes | — |
| `created_at` | `z.string()` | yes | — |
| `updated_at` | `z.string()` | yes | — |
| `tasks` | `z.array(TaskSchema)` | yes | — |

No defaults on any field. The handler (`src/mcp/plan-server.ts:436-445`) passes
raw input straight through `TaskListSchema.parse()`, then writes it unchanged.
`StageRunStore.writeTaskList()` stamps only the event `at` field, not the
`created_at`/`updated_at` on the task list itself.

The manager prompt (`src/agents/manager.ts:171`) tells agents:

> *"call stage_write_tasks({ task_list }) with a TaskList object for …
> containing stage_id, created_at, updated_at, and tasks."*

**[REVIEW]** The plan correctly identifies this. Three gates to update: Zod
schema, JSON Schema tool description, and the manager prompt.

Target exposed input:

```ts
stage_write_tasks({ task_list: { stage_id?, tasks } })
```

Runtime behavior:

- Use active manager stage when `stage_id` is omitted and context has
  `stageId`.
- Stamp `created_at` and `updated_at` at write time.
- **[REVIEW]** On replacement/update (an existing `tasks.json` already present),
  preserve the original `created_at` and update only `updated_at`. This
  requires a read-before-write in `StageRunStore.writeTaskList`, which
  currently just overwrites.
- Persist canonical `TaskListSchema` unchanged.

### Stage Dispatch

**Current schema** (`src/agents/dispatch-tool-schemas.ts:6-30`,
`RUN_MANAGER_SCHEMA`):

```ts
required: ["id", "objective", "starting_points", "expected_outcomes",
            "acceptance_criteria", "references", "tags"]
```

**Current normalization** (`src/agents/manager.ts:131-141`,
`normalizeStage`):

```ts
starting_points: raw.starting_points ?? [],
expected_outcomes: raw.expected_outcomes ?? [],  // but StageSchema requires .min(1)
acceptance_criteria: raw.acceptance_criteria ?? [], // but StageSchema requires .min(1)
references: raw.references ?? [],
tags: raw.tags ?? [],
```

**[REVIEW]** `StageSchema` has `.min(1)` on `expected_outcomes` and
`acceptance_criteria`. The normalization defaults them to `[]`, which would fail
`StageSchema.parse()`. However, by the time `normalizeStage` runs, the stage
has already been validated through `plan_add_stage` / `plan_init`, so this
normalization only applies to the `run_manager` dispatch input path, where the
stage is *already looked up from the plan* via `assertStageDispatchable`. The
`normalizeStage` default for `expected_outcomes` to `[]` is therefore dead
code in normal flow — but it's still misleading. The plan must keep
`expected_outcomes` and `acceptance_criteria` required.

Target behavior:

- Keep `id`, `objective`, `expected_outcomes`, and `acceptance_criteria` required
  in both JSON Schema and Zod.
- Default `starting_points`, `references`, and `tags` to `[]` in JSON Schema
  (remove from `required`) and rely on normalization.
- Persist strict `StageSchema` unchanged.

### Worker Dispatch

**Current schema** (`src/agents/dispatch-tool-schemas.ts:116-144`,
`makeWorkerDispatchSchema`):

```ts
required: ["id", "objective", "files", "instructions", "acceptance_criteria"]
```

**Current normalization** (`src/agents/task-report.ts:25-61`, `normalizeTask`):

- `files` and `instructions` are folded into `description` text.
- `acceptance_criteria` strings are converted to `ChecklistItem` objects with
  `required: true`.
- `id` defaults to `"unknown"`.
- All other fields have defaults.

**[REVIEW]** `buildWorkerDispatchSpec` (`src/server/agent-orchestrator.ts:329-373`)
validates `stageId` and `task.id` as non-empty strings, and requires a non-empty
description from `{description, objective, title, name, instructions}`. It does
**not** require `files`, `instructions`, or `acceptance_criteria` at the
validation level — only the JSON Schema marks them required, which forces LLMs
to include them even though normalization handles their absence gracefully.

Target behavior:

- Keep `stageId` required in JSON Schema.
- Keep a task description/objective required (can come from description,
  objective, title, name, or instructions).
- Make `files`, `instructions`, and `acceptance_criteria` optional in the JSON
  Schema (remove from `required` array).
- Keep `task.id` required for traceability; lower priority to make it optional.

## Adversarial Review Findings

### R1: Escalation is Not a Standalone Tool

The original plan had a standalone "Escalations" section that implied escalation
might be a separate tool. It is not. `EscalationSchema` is embedded inside
`StageSummarySchema` as `escalation: EscalationSchema.optional()`. The manager
writes escalation data as part of `stage_write_summary`. There is no `escalate`
tool. The enrichment of `created_at` on escalations must be handled within the
StageSummary write path, not as a separate handler.

### R2: `ToolCallContext` Already Exists with `role` and `stageId`

The original plan proposed a new `ArtifactWriteContext` interface. But
`ToolCallContext` (`src/mcp/toolContext.ts:17-47`) already has:

```ts
interface ToolCallContext {
  role: AgentRole;
  agentId: string;
  projectRoot: string;
  author?: string;
  stageId?: string;
  channelId?: string;
  sessionId?: string;
  operatorContext?: boolean;
}
```

The real problem is that **bootstrap.ts** (`src/server/bootstrap.ts:443`) strips
this context to `{ agentId: ctx?.agentId }` when calling
`planService.handleToolCall()`. Everything else — `role`, `stageId`,
`projectRoot` — is discarded. The fix should extend the plan-service handler opts
to accept the full `ToolCallContext` (or at least the fields needed for
enrichment), not invent a new interface.

Timeline context (`startedAt`, `startMs`) is not in `ToolCallContext` and never
will be — it belongs to the agent lifecycle, not the tool-call context. The
plan must address how to pass timing from `WorkerAgent.executeTask()` and
`ManagerAgent.run()` into the tool-call path.

### R3: Three Validation Gates Must All Change

Changes must touch all three gates in lockstep:

1. **Zod schema** (what `Schema.parse()` enforces at runtime).
2. **JSON Schema** in `inputSchema` (what the LLM sees as required fields).
3. **Prompt text** (what instructions tell the LLM to include).

The original plan treated these implicitly but didn't call them out as a
coordination requirement. Missing any one means the LLM either fabricates the
old fields, receives schema errors, or gets conflicting instructions.

### R4: Manager Prompt Explicitly Requests Runtime-Owned Fields

`src/agents/manager.ts:171`:

> *"call stage_write_tasks({ task_list }) with a TaskList object for …
> containing stage_id, created_at, updated_at, and tasks."*

`prompts/manager.md:115-132`:

> *"The escalation block itself requires stage_id, reason,
> attempted_remediations, created_at…"*

Both must be updated in Phase 3.

### R5: `normalizeInspectionRequest` Defaults `id` to `"unknown"`

`src/agents/inspector.ts:88`:

```ts
id: (raw.id as string | undefined) ?? "unknown",
```

The `"unknown"` default is worse than omitting the field — it creates a
meaningless identifier that pollutes event logs and makes tracing impossible.
The plan must generate a proper ID (the `inspectionId()` function already exists
in `src/server/cli-actions.ts:100` and generates `"insp-<random>"`).

### R6: Timing Context Does Not Flow Through Tool Calls

`WorkerAgent.executeTask()` captures `startedAt` and `startMs` at
`src/agents/worker.ts:167-168`. `ManagerAgent.run()` captures `startedAt` and
`start` at `src/agents/manager.ts:72-73`. But these lifecycle values are never
propagated to `PlanService.handleToolCall()` — they remain local to the agent's
`run()` method.

The fix requires:

- The agent must make timing available to the tool-call dispatch path.
- Options: (a) store it on `AgentContext`, (b) store it on `BaseAgent` and
  pass it through the `McpRuntime.callTool` path, or (c) have the writer
  handler compute `completed_at` and `duration_ms` at write time, using
  `started_at` from the context to compute duration.
- Option (c) is simplest: the enrichment step computes `completed_at` at write
  time and uses `startedAt` from the agent lifecycle to compute `duration_ms`.
  But this means `started_at` must flow from the agent to the handler.

### R7: Failure/Abort Paths Already Inject Timing — Success Path Doesn't

`buildFailureReport()` (`src/agents/task-report.ts:68-93`) and
`buildFailureSummary()`/`buildAbortSummary()` (`src/agents/manager.ts:181-223`)
already inject `started_at`, `completed_at`, `duration_ms`, `task_id`,
`stage_id`, and `agent` from runtime context. The success paths (LLM-written
artifact read from disk) do not. This means:

- **Failure and abort artifacts are always correctly timestamped.**
- **Successful artifacts only have correct timestamps when the LLM happens to
  fabricate plausible ones.**

The enrichment must replicate the failure-path injection pattern for the
success path.

### R8: `StageRunStore.writeTaskList` Doesn't Read Before Write

The current `writeTaskList()` (`src/store/stage-run-store.ts:199-211`) just
writes without checking if a task list already exists. The proposed behavior of
"preserve existing `created_at` on update" requires adding a read-before-write
step. This is a new code path, not just a schema change.

### R9: `bootstrap.ts` Discards Most `ToolCallContext`

The plan-service route in `src/server/bootstrap.ts:443`:

```ts
planService.handleToolCall(toolName, args, { agentId: ctx?.agentId }),
```

This discards `ctx?.role`, `ctx?.stageId`, `ctx?.projectRoot`, etc. To inject
`role`, `stageId`, and `agentId` into writer tools, the full `ToolCallContext`
(or at minimum `role`, `agentId`, `stageId`) must be forwarded.

### R10: `TaskSchema` Defaults Are Already Present

`src/types.ts:124-138`: `TaskSchema` already has `.default([])` on `checklist`,
`dependencies`, `tags`; `.default("pending")` on `status`; `.default(1)` on
`attempt`; `.default(3)` on `max_attempts`; `.optional()` on `started_at` and
`completed_at`. The worker dispatch tool schema doesn't reflect these defaults,
but `normalizeTask` handles them. The plan's Phase 4 changes to the worker
dispatch JSON Schema should align with these existing Zod defaults.

### R11: `expected_outcomes` and `acceptance_criteria` Have `.min(1)` Constraint

`StageSchema` declares:

```ts
expected_outcomes: z.array(z.string()).min(1),
acceptance_criteria: z.array(z.string()).min(1),
```

The plan correctly keeps these required. But `normalizeStage` defaults them to
`[]`, which would fail `StageSchema.parse()`. This is dead code in normal flow
(stages are validated before they reach normalization), but the `normalizeStage`
defaults should be fixed to avoid future confusion.

### R12: `plan_complete_stage` Already Stages Timing Correctly

`PlanService.plan_complete_stage()` (`src/mcp/plan-server.ts:242-315`) already
computes `completed_at: now` and uses `stage.started_at` from the plan. This is
the canonical pattern for how stage-level timing should work. The StageSummary
enrichment should follow the same approach.

## Implementation Plan

The fix should be implemented in small, reviewable slices. The first slice must
solve plumbing, because schema changes without runtime context would only move
validation failures to a different layer.

### Step 1: Add Plan Tool Runtime Context

Purpose: make plan writer tools aware of the caller and the active agent
lifecycle without weakening persisted schemas.

Code touchpoints:

- `src/mcp/plan-server.ts`
- `src/mcp/plan-registry.ts`
- `src/server/bootstrap.ts`
- `src/mcp/toolContext.ts` if a shared type is needed

Add a plan-writer options type. `ToolCallContext` remains the caller identity
source; `ArtifactExecutionContext` carries per-task/per-stage execution state
that is not part of the generic tool-call context.

```ts
interface ArtifactWriteTiming {
  startedAt: string;
  startMs: number;
}

interface ArtifactExecutionContext {
  stageId?: string;
  taskId?: string;
  timing?: ArtifactWriteTiming;
}

interface PlanToolCallOptions {
  ctx?: ToolCallContext;
  artifact?: ArtifactExecutionContext;
}
```

Implementation details:

- Change `PlanToolEntry.handler()` and `dispatchPlanToolCall()` to accept
  `PlanToolCallOptions` instead of `{ agentId?: string }`.
- Change `PlanService.handleToolCall()` and stage artifact writer methods to
  accept `PlanToolCallOptions`.
- Forward the full `ToolCallContext` from `src/server/bootstrap.ts` instead of
  reducing it to `{ agentId: ctx?.agentId }`.
- Preserve event attribution by using `opts.ctx?.agentId` where current code
  uses `opts.agentId`.
- Do not put `taskId`, `startedAt`, or `startMs` on `ToolCallContext`; those
  belong to the current artifact execution, not every tool call.

Acceptance criteria:

- Existing plan tools still work when called without context.
- Existing event attribution still records the same `agent_id` values.
- Plan tools can inspect `opts.ctx?.role` and `opts.ctx?.stageId`.

### Step 2: Make Agent Lifecycle Timing Reach Writer Tools

Purpose: give `task_write_report` and `stage_write_summary` enough timing data
to inject canonical `started_at`, `completed_at`, and `duration_ms`.

Code touchpoints:

- `src/agents/base.ts`
- `src/agents/worker.ts`
- `src/agents/manager.ts`
- MCP runtime/tool-call path used by `BaseAgent.runLoop()`

Implementation details:

- Add an optional per-agent artifact execution slot to `BaseAgent` or the
  internal tool-call dispatch context used by `BaseAgent`.
- In `WorkerAgent.executeTask()`, set that slot immediately after capturing
  `startedAt` and `startMs`; include `stageId: input.stageId` and
  `taskId: input.task.id`; clear it in a `finally` block after the task loop
  completes.
- In `ManagerAgent.run()`, set that slot immediately after capturing
  `startedAt` and `start`; include `stageId: stage.id`; clear it in a `finally`
  block after the manager loop completes.
- Ensure the artifact execution slot is copied into
  `PlanToolCallOptions.artifact` only for in-process plan tools.
- Keep failure/abort helper functions unchanged. They already produce canonical
  artifacts directly.

Acceptance criteria:

- During `task_write_report`, the handler can see the worker task id, stage id,
  and start time.
- During `stage_write_summary`, the handler can see the manager stage start
  time.
- Timing context is not leaked across follow-up tasks or reused worker turns.

### Step 3: Add Agent-Facing Input Schemas

Purpose: separate semantic agent inputs from strict persisted artifacts.

Code touchpoints:

- `src/types.ts`, or a new `src/mcp/plan-input-schemas.ts` if keeping persisted
  types separate is clearer
- tests under `src/**.test.ts`

Add schemas:

- `TaskListInputSchema`: `{ stage_id?: string; tasks: Task[] }`
- `TaskReportInputSchema`: semantic report fields only; array fields default
  to `[]`; no `task_id`, `stage_id`, `agent`, `started_at`, `completed_at`,
  `duration_ms`
- `EscalationInputSchema`: no `created_at`; `stage_id` optional; `task_id`

Keep unchanged:

### Step 4: Enrich and Persist Stage Artifact Writes

Purpose: overwrite runtime-owned metadata before canonical validation and
storage.

Code touchpoints:

- `src/mcp/plan-server.ts`
- `src/store/stage-run-store.ts`
- `src/types.ts` or new schema module from Step 3

Implement helper functions near the plan service or in a small focused module:

```ts
function nowFromRuntime(): string
function elapsedMs(startMs: number): number
function requireStageId(inputStageId: string | undefined, opts: PlanToolCallOptions): string | PlanError
function requireWorkerIdentity(opts: PlanToolCallOptions): WorkerRole | PlanError
function requireTiming(opts: PlanToolCallOptions): ArtifactWriteTiming | PlanError
```

`stage_write_tasks` behavior:

- Parse with `TaskListInputSchema`.
- Determine `stage_id` from `input.stage_id ?? opts.artifact?.stageId ?? opts.ctx?.stageId`.
- Determine `now = new Date().toISOString()`.
- Read existing task list if present.
- Set `created_at = existing.created_at ?? now`.
- Set `updated_at = now`.
- Validate with `TaskListSchema`.
- Persist with `StageRunStore.writeTaskList()`.

`task_write_report` behavior:

- Parse with `TaskReportInputSchema`.
- Determine `task_id` from `opts.artifact?.taskId`, not from the LLM input.
- Determine `stage_id` from `opts.artifact?.stageId ?? opts.ctx?.stageId`.
- Determine `agent` from `opts.ctx?.role`; reject if not a worker role.
- Require `opts.artifact?.timing` for agent-originated writes; for explicit
  operator/admin repair calls, either reject semantic input without timing or
  use a documented fallback of `started_at = completed_at` and
  `duration_ms = 0`.
- Compute `completed_at = new Date().toISOString()`.
- Compute `duration_ms = Date.now() - timing.startMs`.
- Set `started_at = timing.startedAt`.
- Validate with `TaskReportSchema`.
- Persist with `StageRunStore.writeTaskReport()`.

`stage_write_summary` behavior:

- Parse with `StageSummaryInputSchema`.
- Determine `stage_id` from `input.stage_id ?? opts.artifact?.stageId ?? opts.ctx?.stageId`.
- Require or explicitly fallback timing as above.
- If `summary.escalation` exists, set `escalation.stage_id = stage_id` and
  `escalation.created_at = completed_at` unless a more precise timestamp is
  chosen.
- Validate with `StageSummarySchema`.
- Persist with `StageRunStore.writeStageSummary()`.

Important design rule:

- If the agent provides runtime-owned fields in a stale full-canonical payload,
  overwrite them. Do not trust them. Optionally add a debug log, but do not fail
  solely because stale fields are present.

Acceptance criteria:

- Agent-written successful reports and summaries get runtime timestamps.
- Agent-written task lists get runtime `created_at` and `updated_at`.
- Existing full canonical payloads still succeed, but runtime-owned values are
  overwritten.

## Risks

### Risk: Tool context does not currently carry enough metadata

Plan writer tools may not receive task ID, stage ID, role, or timing unless
that context is explicitly passed from the agent runtime.

**Mitigation:**

- Extend `PlanService.handleToolCall()` opts to accept `ToolCallContext`
  (already has `role`, `agentId`, `stageId`) plus optional
  `ArtifactExecutionContext` for current `stageId`, `taskId`, and timing.
- Forward full context from `src/server/bootstrap.ts:443` instead of stripping
  to just `agentId`.
- For artifact execution state (`taskId`, `startedAt`, `startMs`), have agents
  pass it as a parameter at the point where they know it — at the start of
  `executeTask()` / `run()`.
- Keep fallback behavior for operator/admin contexts where timing isn't
  available (use `Date.now()` for `completed_at` and skip `duration_ms` or
  approximate it).

### Risk: Backward-compatible full payload acceptance hides agent mistakes

If writer tools continue accepting full canonical payloads, agents may still
fabricate metadata.

**Mitigation:**

- Remove runtime-owned fields from input schemas and prompts.
- **Always overwrite** runtime-owned fields if present, never trust them.
- log a debug-level diagnostic when runtime-owned fields are present in input
  (to surface stale agent behavior during rollout).

### Risk: Generated IDs reduce traceability

Automatically generated task IDs can make task references less meaningful.

**Mitigation:**

- Keep manager-authored task IDs preferred.
- Only generate IDs when omitted.
- Use stable prefixes such as `task-<short-id>`.

### Risk: Existing tests assume strict input equals strict persistence

Tests may need to distinguish input validation from persisted artifact
validation.

**Mitigation:**

- Add input-schema tests.
- Keep persistence-schema tests unchanged.
- Ensure failure/abort-path tests continue to pass (they construct canonical
  artifacts directly).

### Risk: normalizeStage defaults conflict with StageSchema constraints

`normalizeStage` defaults `expected_outcomes` and `acceptance_criteria` to `[]`,
but `StageSchema` requires `.min(1)`. While this is dead code in normal flow
(stages are validated through plan tools before reaching normalization), it
creates a misleading maintenance trap.

**Mitigation:**

- Remove or document the dead-code defaults in `normalizeStage`.
- Keep `expected_outcomes` and `acceptance_criteria` required in all schemas.

### Risk: Escalation enrichment must be part of StageSummary, not standalone

`EscalationSchema` is embedded inside `StageSummarySchema`. The enrichment of
`created_at` and `stage_id` on escalation objects must happen within the
StageSummary write path, not as a separate handler. If treated independently,
the enrichment will be missed.

**Mitigation:**

- Handle escalation enrichment inside `stage_write_summary` enrichment.
- No separate escalation tool or handler.

## Suggested Priority Order

1. **Shell command log contract** — already aligned; no further work needed.
2. **Fix context propagation plumbing** — extend `handleToolCall` opts to
  accept `ToolCallContext` plus `ArtifactWriteTiming`. This is a prerequisite
  for all enrichment phases.
3. **Fix `TaskReport` input enrichment** — worker failures after useful work
  are the most expensive; the failure path already injects timing.
4. **Fix `StageSummary` input enrichment** — gates stage completion; the
  failure/abort path already injects timing.
5. **Fix `TaskList` timestamp injection** — managers currently fabricate
  timestamps at every stage start.
6. **Fix `normalizeInspectionRequest`** — replace `"unknown"` ID default with
  `inspectionId()`.
7. **Relax inspector dispatch schema** — remove runtime-owned `required`
  fields.
8. **Relax stage and worker dispatch optional arrays/text fields** — align
  JSON Schema with existing normalization.
9. **Reassess `git_commit` and role write territories separately** — these
  are policy/routing rather than runtime-owned metadata.

## Success Criteria

The remediation is complete when:

- No LLM-facing tool schema requires runtime-owned metadata.
- No prompt text instructs agents to fabricate timestamps, durations, IDs, or
  internal paths.
- No JSON Schema marks runtime-owned fields as `required`.
- Runtime-generated metadata appears correctly in persisted canonical artifacts.
- Existing persisted state remains readable.
- Failure/abort paths continue to produce correctly-timestamped artifacts.
- PM-style stages can proceed without agents fabricating timestamps, durations,
  or internal log paths.
- `normalizeInspectionRequest` no longer defaults `id` to `"unknown"`.
